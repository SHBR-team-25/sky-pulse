## Функциональные требования

### Обязательные (MVP)

**FR1.** Система должна отображать на карте текущие позиции самолётов на основе живого потока данных.

**FR2.** Позиция самолёта на карте должна включать координаты, курс (heading) и высоту.

**FR3.** Система должна обогащать событие о позиции самолёта данными из справочника воздушных судов (тип самолёта, авиакомпания) по ключу `icao24`.

**FR4.** Если борт не найден в справочнике воздушных судов, система должна всё равно отобразить его на карте с сокращённым набором полей, не отбрасывая событие.

**FR5.** Пользователь должен иметь возможность кликнуть на самолёт на карте и увидеть карточку с позывным, типом воздушного судна и авиакомпанией.

**FR6.** Система должна получать позиции самолётов у OpenSky через аккаунт, зарегистрированный на пайплайн (не на пользователя сайта).

**FR7.** Система должна ограничивать частоту и площадь запросов к OpenSky в зависимости от суточного лимита выбранного уровня аккаунта.

**FR8.** Система должна отображать на дашборде минимум одну аналитику поверх исторических данных — самые загруженные аэропорты за период.

### Опциональные (простор для творчества из ТЗ)

**FR9.** Система должна определять аэропорт вылета борта по переходу состояния `on_ground` из «true» в «false» и сопоставлению последней позиции борта перед взлётом с ближайшим аэропортом из справочника.

**FR10.** Система должна вычислять коэффициент загруженности аэропорта: до накопления 14 дней истории — по фиксированным пороговым диапазонам, откалиброванным по категории аэропорта (`type` из OurAirports: large/medium/small_airport) на основе реальной выборки данных, а не произвольно; после накопления истории — по скользящему 90-му процентилю индивидуально для каждого аэропорта, раздельно для дня и ночи.

**FR11.** Система должна строить траекторию борта на основе накопленной истории позиций, не используя внешний экспериментальный эндпоинт OpenSky `/tracks`.

**FR12.** Пользователь должен иметь возможность просматривать список аэропортов с фильтрацией по названию, городу и стране.

**FR13.** Пользователь должен иметь возможность независимо включать и выключать отображение отдельных слоёв статистики на карте (тепловая карта, маршруты и т.д.).

**FR14.** Система должна обогащать событие данными о стране регистрации и, опционально, ближайшем аэропорте.

## Нефункциональные требования

**NFR1.** Задержка между событием и его отображением на карте не должна превышать нескольких десятков секунд (явный SLA из ТЗ).

**NFR2.** Данные для аналитики дашборда должны пересчитываться не реже одного раза в час.

**NFR3.** Сбой и перезапуск джобы обогащения или поставщика не должны приводить к молчаливой потере данных (задвоения допустимы для позиций на карте — там ок at-least-once; для витрин дашборда лучше избегать дублей).

**NFR4.** Система должна соблюдать суточный лимит запросов OpenSky и не блокироваться источником.

**NFR5.** При временной недоступности OpenSky система должна продолжать отдавать последние известные позиции, не останавливая работу целиком.

**NFR6.** Проект должен разворачиваться по инструкции из README на локальном YTsaurus с нуля (форкабельность — явное требование).

**NFR7.** Пайплайн должен укладываться в выделенную квоту кластера, не требуя больше ресурсов, чем реально выделено команде.
