# Pipeline handoff

## Контекст

Pipeline получает наблюдения OpenSky, обогащает их справочником воздушных судов,
сегментирует последовательности позиций в рейсы и строит витрины дашборда в YTsaurus.
OpenSky остаётся источником истины, поэтому качество результата ограничено качеством,
частотой и последовательностью входных наблюдений.

Основные джобы:

- `spyt/jobs/streaming_job.py` читает очередь `positions_raw`, обогащает позиции через
  `ref_aircraft` и записывает `positions_history` и `positions_current`.
- `spyt/jobs/job_segment.py` запускается раз в 15 минут и превращает историю позиций
  в открытые и завершённые рейсы и события аэропортов.
- `spyt/jobs/job_aggregate.py` запускается раз в 5 минут и пересчитывает витрины дашборда.

Схемы таблиц находятся в `bootstrap_service/schemas.py`. Скрипты создания таблиц
находятся рядом с bootstrap service.

## Принятые решения для job_segment

- Рейс начинается только по свежему переходу `on_ground: true → false`.
- Борт, впервые замеченный в воздухе, получает открытый рейс с неизвестным аэропортом
  вылета. Состояние из одной airborne-точки считается provisional: если новых точек
  не появится, оно удаляется по таймауту без записи сегмента и событий.
- В `flights_open` хранится состояние открытого рейса и предыдущая обработанная точка.
  Состояние переживает границы batch-запусков; локальная переменная предыдущей точки
  сама по себе между запусками не сохраняется.
- Разрыв между точками больше `MAX_TRANSITION_GAP_SECONDS` не считается надёжным
  доказательством взлёта или посадки и разрывает непрерывный трек, даже если
  `FLIGHT_TIMEOUT_SECONDS` ещё не истёк. Timeout управляет временем хранения
  состояния, а не допустимым интервалом между точками одного рейса.
- Первая airborne-точка является provisional-кандидатом. Ground-точка не может
  подтвердить такой кандидат: для подтверждения рейса нужна вторая airborne-точка.
- Посадка подтверждается двумя последовательными ground-точками либо ground-точкой
  и достаточно долгой стоянкой.
- Короткая последовательность `airborne → ground → airborne` считается шумом.
- Короткая последовательность `ground → airborne → ground` также считается шумом,
  если оба определённых аэропорта совпадают и длительность не превышает
  `GROUND_GLITCH_MAX_SECONDS`.
- Смена callsign обновляет метаданные, но не закрывает рейс. Callsign может меняться,
  исчезать или нормализоваться во время одного физического рейса, поэтому он слишком
  ненадёжен как самостоятельная граница.
- Точки внутри борта обрабатываются по event time, но watermark служит курсором по
  `enriched_at`, чтобы поздно записанная streaming job строка не была потеряна.
  Watermark обновляется только после успешной записи результатов.
- `positions_history` — dynamic table с ключом `(icao24, time_position)`: повторная
  запись заменяет строку и обновляет `enriched_at`, поэтому она снова попадает в
  enrichment-watermark batch. Для открытого рейса повтор отбрасывается условием
  `time_position <= last_ts`; ground-точка без открытого рейса ничего не создаёт.
  Это делает обычные повторы безопасными, хотя не заменяет полноценный учёт
  обработанных версий ключа при конфликтующих повторных значениях.
- Идентификатор рейса детерминирован по `icao24` и времени начала.
- Закрытые рейсы удаляются из dynamic table `flights_open` явным `delete_rows`.
  Python-клиент драйвера берёт токен SPYT из `YT_SECURE_VAULT_YT_TOKEN`, с fallback
  на `YT_TOKEN` для локального запуска; отсутствие credentials завершается сразу,
  а не уходит в длительные HTTP-ретраи.
- Радиус аэропорта, таймаут, максимальный разрыв, подавление ground-глитча и допустимое
  опоздание вынесены в переменные окружения.
- Отдельная очистка зависших `flights_open` не нужна: цикл обходит объединение
  бортов из нового batch и всех состояний `flights_open`. Даже при пустом batch
  вызывается `process_aircraft_points(..., points=[])`, где `until_ts - last_ts`
  сравнивается с timeout. Подтверждённый воздушный трек у границы области закрывается
  как `bbox_exit`, внутри неё — как `observation_lost`; одноточечный кандидат
  отбрасывается. Состояние с последней ground-точкой закрывается как `landing`.
  Если segment scheduler продолжает работать,
  при остановке OpenSky `flights_open` со временем станет пустой.

Конфигурация по умолчанию:

```text
AIRPORT_RADIUS_KM=15
FLIGHT_TIMEOUT_SECONDS=1800
MAX_TRANSITION_GAP_SECONDS=300
GROUND_GLITCH_MAX_SECONDS=60
ALLOWED_LATENESS_SECONDS=120
BBOX_EXIT_MARGIN_KM=25
```

## Принятые решения для job_aggregate

- `active_flights`, `airborne`, `on_ground`, средние показатели, набор, снижение и
  emergency squawks — моментальный snapshot по свежим строкам `positions_current`.
- `active_flights` равен `airborne`; `dashboard_trend.active_aircraft` получает то же
  значение. `flights_open` для dashboard snapshot не используется.
- Для каждого `icao24` используется только самая свежая допустимая позиция.
- Перед автоматическим выбором `computed_at` весь `positions_current` материализуется
  в cache. Поэтому streaming job не может заменить строки между выбором времени и
  фактическим Spark action. Автоматический `computed_at` не меньше максимального
  `time_position` зафиксированного snapshot, что также покрывает небольшой clock skew.
- Позиции старше `POSITION_FRESHNESS_SECONDS` и позиции из будущего исключаются.
- Средняя высота и скорость считаются только по свежим бортам в воздухе.
- Набор и снижение считаются только для воздушных бортов.
- События и сегменты выбираются из замкнутого интервала
  `[computed_at - DASHBOARD_WINDOW_SECONDS, computed_at]`.
- События без аэропорта, `flight_id` или корректного направления исключаются.
- Рейсы считаются через уникальный `flight_id`, чтобы повторная строка не увеличивала
  статистику.
- Пустые наборы дают нулевые счётчики. Средние значения при отсутствии воздушных
  бортов остаются `null`.
- `dashboard_routes` исключает same-airport сегменты с `point_count < 3`; они
  остаются в истории для диагностики, но не считаются надёжным маршрутом.
- Пустое имя производителя и отсутствие записи в `ref_aircraft` дают `Unknown`.
- Порядок топов детерминирован дополнительной сортировкой по ключам.

Конфигурация по умолчанию:

```text
DASHBOARD_WINDOW_SECONDS=86400
POSITION_FRESHNESS_SECONDS=900
AGGREGATE_INTERVAL_SECONDS=300
```

## Streaming job

Стриминговая джоба упала в YTsaurus по `Memory limit exceeded` на драйвере.
У упавшего запуска было `spark.driver.memory=1G`, общий лимит контейнера
около 1.4 GiB, Java RSS достиг примерно 1.45 GB, а Python ещё 49 MB. Также был
один executor с одним core. Trigger был 10 секунд, но каждый microbatch
занимал 45–60 секунд, поэтому queue consumer отставал.

Явной Python-утечки или `collect()` в streaming job нет. Отстающие данные остаются
в queue, а не копятся как Python-объекты драйвера. Основной диагноз —
слишком маленький driver container без запаса на non-heap/native/Python память
в сочетании с недостаточной пропускной способностью.

Внесены изменения:

- `run_streaming.py` теперь передаёт driver memory/overhead, executor memory/cores,
  число executor'ов и `spark.sql.shuffle.partitions`;
- по умолчанию: driver heap 2 GiB, driver overhead 1 GiB, два executor'а,
  по 2 core и 4 GiB на executor, 8 shuffle partitions;
- trigger увеличен с 10 до 30 секунд, чтобы амортизировать высокую
  фиксированную стоимость YTsaurus-записей и checkpoint;
- источнику задан `max_rows_per_partition=50000`, чтобы после простоя один
  microbatch не пытался забрать весь backlog;
- `enriched_df.unpersist()` перенесён в `finally`, чтобы cache снимался и при
  ошибке одной из двух записей;
- все настройки вынесены в CLI и `STREAMING_*` environment variables, задокументированы
  в `.env.example` и `spyt/README.md`.
- YTsaurus Shuffle на demo-кластере отключён: его `StartShuffle` требует
  `SupervisorService.GenerateSignature`, а кластер отвечает
  `Signature generation is unsupported`. Node-local внешний Spark Shuffle Service
  также отключён, поскольку он не видит `.index` в изолированном `/tmp` executor'а.
- После отключения этих двух механизмов Spark всё ещё падал на batch 195 с
  `FetchFailedException`, причиной которого был `NoSuchFileException` для
  `/tmp/.../shuffle_*.index`. Оба executor'а оказались на одном YTsaurus exec-node.
  Spark 4.2 по умолчанию применил отдельную оптимизацию host-local shuffle read:
  executor пытался напрямую открыть файл соседа на том же host вместо сетевого
  запроса к его BlockManager. В YTsaurus sandbox локальные `/tmp` изолированы даже
  при одинаковом hostname, поэтому этот файл для соседа отсутствует. Добавлен
  `spark.shuffle.readHostLocalDisk=false`. Теперь при фиксированных executor'ах
  shuffle-блоки должны запрашиваться по сети у BlockManager владельца; dynamic
  allocation для этой конфигурации включать нельзя.

Безусловный broadcast join для `ref_aircraft` не добавлялся. Справочник OpenSky
содержит сотни тысяч строк и десять строковых полей. Без замера размера
принудительный broadcast сам может увеличить память драйвера. Оставлен обычный
left join.

После развёртывания нужно проверить:

- в параметрах operation есть `-Xmx2g`, driver limit около 3 GiB, два executor'а
  по 2 core;
- driver RSS после первоначального роста выходит на плато, а не растёт от батча к батчу;
- `processedRowsPerSecond > inputRowsPerSecond`, consumer lag уменьшается, а после
  разбора backlog microbatch стабильно укладывается в 30 секунд.
- в Spark Environment присутствуют все три настройки:
  `spark.ytsaurus.shuffle.enabled=false`, `spark.shuffle.service.enabled=false` и
  `spark.shuffle.readHostLocalDisk=false`; в новых ошибках отсутствует стек
  `getHostLocalShuffleData` / `fetchHostLocalBlock`.

Запускать без `--skip-upload`, с прежними consumer и checkpoint. Checkpoint и consumer
не удалять, чтобы продолжить с сохранённого offset.

Проверено:

- известный борт обогащается полями `ref_aircraft`;
- неизвестный борт сохраняется благодаря left join;
- строка с `null icao24` не теряется;
- исходные поля позиции сохраняются;
- `enriched_at` заполняется Unix timestamp;
- все пути запуска обязательны и корректно разбираются.

Обработчик `foreachBatch` вложен в `main`, а запись использует YTsaurus Data Source.
Поэтому запись в `positions_history`, выбор самой свежей строки для
`positions_current`, checkpoint и продвижение queue consumer нельзя честно проверить
обычным локальным unit-тестом без изменения production-кода или тестового YTsaurus.
Это остаётся интеграционным сценарием.

## Оставшиеся риски

- Запись нескольких выходных таблиц одной джобы не атомарна. Падение между записями
  может временно оставить таблицы разных поколений. Для строгой атомарности нужны
  staging-таблицы и переключение поколения на уровне YTsaurus или потребителя.
- `dashboard_trend` дописывается отдельно. Повтор запуска с другим `computed_at`
  создаст ещё одну точку; повтор с тем же ключом зависит от семантики записи dynamic
  table.
- Корректность streaming-записи, checkpoint и queue consumer должна проверяться
  интеграционным тестом на YTsaurus.
- `job_segment` продвигает event-time watermark по настенному времени даже при
  пустом `positions_history`. Если streaming job потом допишет backlog со старым
  `time_position <= watermark`, segment job его уже не обработает. Это отдельный
  архитектурный риск.
- Справочник `ref_aircraft` предполагает одну строку на `icao24`. Дубликаты в
  справочнике могут размножить строки после join в streaming job.
- OpenSky может присылать ошибочный `on_ground`, координаты, callsign или редкие
  наблюдения. Segment job подавляет известные классы шума, но не может восстановить
  факты, которых нет во входных данных.

## OOM job_segment в режиме OpenSky all — 20 августа 2026

При 12 тысячах позиций за snapshot и запуске segment раз в 15 минут driver operation
упал с `Memory limit exceeded`: лимит контейнера был 1.4 GiB, Java с heap 1 GiB
заняла около 1.13 GiB RSS, Python — около 414 MiB, суммарное usage — около 1.54 GiB.
Указанные в operation `spark.executor.memory=4G` относятся к executor и не увеличивают
лимит driver-контейнера.

Кроме недостаточного лимита обнаружена причина роста Python/JVM driver: job делала
`collect()` всего batch и строила `points_by_aircraft`. При snapshot каждые 5 секунд
это 2.16 млн строк за 15 минут. Теперь отсортированные строки читаются через
`toLocalIterator()` и на драйвере одновременно хранится только трек одного борта.
Открытые состояния без новых точек по-прежнему отдельно проходят timeout-обработку.

Для segment добавлены отдельные ресурсы launcher-а и env defaults:

```text
SEGMENT_DRIVER_MEMORY=4g
SEGMENT_DRIVER_MEMORY_OVERHEAD=2g
SEGMENT_EXECUTOR_MEMORY=4g
SEGMENT_EXECUTOR_CORES=2
SEGMENT_NUM_EXECUTORS=2
SEGMENT_SHUFFLE_PARTITIONS=16
```

Это стартовая конфигурация, а не доказанный capacity limit. Для потока 12 тысяч строк
каждые 5 секунд в production рекомендуется также `SEGMENT_INTERVAL_SECONDS=300`,
чтобы один batch содержал около 720 тысяч, а не 2.16 млн строк. После выкладки нужно
замерить duration, peak RSS, input rows и shuffle spill. Условие устойчивости:
segment duration заметно меньше интервала; желателен запас хотя бы 2x.

Проверены `py_compile`, `git diff --check` и smoke-test сформированной команды submit.
Полный pytest не запущен: команда `pytest` отсутствует в текущем окружении.

## Resource recommender и streaming profile для all — 20 августа 2026

Добавлен `scripts/recommend_resources.py`. Он не принимает интерактивный ввод:
читает обязательные `CLUSTER_AVAILABLE_CORES`, `CLUSTER_AVAILABLE_MEMORY_GB`,
`EXPECTED_SNAPSHOT_ROWS` и `OPENSKY_POLL_INTERVAL_SECONDS` из окружения. Скрипт
печатает оценочный rows/s и готовый env-блок. `all` рекомендуется только от 16 cores,
64 GiB и при достаточном числе streaming executors; иначе сохраняется заданный bbox.
Это heuristic initial sizing, а не замена load test.

Streaming defaults повышены для world-wide нагрузки 12 тысяч строк каждые 5 секунд:
driver 3 GiB + overhead 2 GiB, четыре executor по 2 cores / 4 GiB, 32 shuffle
partitions и trigger 15 секунд. `ref_aircraft` теперь один раз repartition-ится,
материализуется и хранится как `MEMORY_AND_DISK`, чтобы не читать и не готовить
статический справочник заново для каждого microbatch. При завершении cache снимается.

В `.env.example` добавлены пустые поля доступных cores/memory и ожидаемый размер
snapshot; README содержит команду запуска и пояснение ограничений рекомендации.
Полный результат тестов после этих изменений: 83 passed, одно предупреждение PySpark
о pandas >= 3.0.

## Инцидент job_segment с зависанием на delete_rows — 19 августа 2026

После замены `mode("overwrite")` на явное удаление закрытых рейсов из dynamic table
`flights_open` новая operation перестала завершаться. Spark успевал прочитать и
обработать данные, после чего Python driver зависал на `delete_rows` с растущими
паузами между повторами: примерно 8, 14, 19, 26, 43, 59, 94 и 151 секунда.

В логах были две связанные ошибки:

- запрос к `//sys/client_config` отвечал `Client is missing credentials`;
- `delete_rows` обращался к внутреннему адресу
  `https://hp-0.http-proxies.hackathon.svc.cluster.local` и получал
  `Connection refused`, после чего YT wrapper запускал экспоненциальные ретраи.

Корневая причина находилась в `spyt/jobs/job_segment.py`: отдельный Python
`YtClient`, добавленный для `delete_rows`, искал только переменную `YT_TOKEN`.
Launcher знает токен и использует его для upload/submit, а внутри SPYT operation
credential драйвера доступен под именем `YT_SECURE_VAULT_YT_TOKEN`. Spark YT Data
Source поэтому продолжал работать, а вручную созданный Python-клиент оставался без
авторизации. Предупреждения о занятых портах `27001`–`27003`, incubator modules и
native Hadoop к зависанию отношения не имеют.

Исправлено:

- `create_yt_client()` сначала читает `YT_SECURE_VAULT_YT_TOKEN`, затем использует
  `YT_TOKEN` как fallback для локального запуска;
- если оба значения отсутствуют, job немедленно завершается с `ValueError`, не
  начиная длительные HTTP-ретраи;
- клиент создаётся только если множество закрытых ключей действительно непустое;
- токен намеренно не передаётся аргументом Python-процесса, чтобы секрет не оказался
  в command line operation;
- mocks тестов `delete_rows` принимают служебный keyword `format="json"`.

Проверены `python3 -m py_compile` для `job_segment.py` и `run_segment.py`, а также
`git diff --check`. Повторный pytest в этой сессии не выполнен: в найденных virtualenv
нет модуля `pytest`. Более ранний полный прогон до этого точечного исправления давал
59 пройденных тестов.

Следующее обязательное действие: остановить старую зависшую operation и запустить
`run_segment.py` без `--skip-upload`, иначе в Cypress останется старая версия
`job_segment.py`. После запуска проверить, что в driver log больше нет

## Хронология инцидентов streaming job

1. Изначально джоба запускалась, но спустя время драйвер завершался по
   `Memory limit exceeded`. У него был heap 1 GiB при лимите контейнера около
   1.4 GiB; Java RSS доходил примерно до 1.45 GB, отдельно работал Python-процесс.
   Одновременно один executor с одним core не успевал за входным потоком:
   microbatch при trigger 10 секунд выполнялся 45–60 секунд, consumer lag рос.
2. Для памяти и пропускной способности выставлены driver heap 2 GiB + overhead
   1 GiB, два executor'а по 2 core и 4 GiB, 8 shuffle partitions, trigger 30 секунд
   и лимит 50 000 строк на партицию source в одном microbatch. Очистка cache через
   `unpersist()` перенесена в `finally`.
3. После перехода на два executor'а shuffle начал падать с отсутствующими локальными
   `.index` в `/tmp`: node-local внешний Spark Shuffle Service не имеет доступа к
   файловым системам изолированных executor sandbox. Его отключили настройкой
   `spark.shuffle.service.enabled=false`.
4. Попытка использовать YTsaurus Shuffle дала другую ошибку: `StartShuffle` вызвал
   `SupervisorService.GenerateSignature`, но demo-кластер ответил
   `Signature generation is unsupported`. Поэтому YTsaurus Shuffle отключили через
   `spark.ytsaurus.shuffle.enabled=false`, оставив оба механизма выключенными.
5. Запуск 18 августа 2026 года дошёл до batch 195, но снова упал с
   `FetchFailedException -> NoSuchFileException: /tmp/.../shuffle_*.index`.
   Это не прежний внешний сервис: стек содержит `getHostLocalShuffleData` и
   `fetchHostLocalBlock`. Spark увидел два executor'а на одном hostname и включил
   независимую host-local оптимизацию, несовместимую с раздельными sandbox `/tmp`.
   Исправление: `spark.shuffle.readHostLocalDisk=false`. После развёртывания это
   исправление ещё требует проверки реальным запуском; старые consumer и checkpoint
   сохраняются.

Предупреждения о занятых портах, `native-hadoop`, невозможности FileContext API,
отключении adaptive execution в streaming и отсутствующем checkpoint child `state`
не являются причиной этого падения. Финальные `ForeachBatchUserFuncException`,
`Py4JJavaError` и `StreamingQueryException` — только оболочки исходного shuffle
`FetchFailedException` во время `.save()`.

При продолжении работы сначала прочитать этот файл, затем посмотреть актуальный код и
запустить `pytest -q`, потому что рабочее дерево могло измениться после этого handoff.

## Исправление active flights в job_aggregate — 19 августа 2026

Симптом: `dashboard_totals.active_flights` и `dashboard_trend.active_aircraft`
становились равны нулю при заполненной `flights_open`.

Проверка исходных определений в `docs/database.md` показала, что `active_flights` —
число наблюдаемых бортов в воздухе, а `positions_current` — текущее состояние бортов.
`flights_open` хранит незавершённые flight-сессии и обновляется segment job, поэтому
для моментального dashboard snapshot семантически не подходит. Заполненность этой
таблицы не доказывает наличие свежей телеметрии в момент расчёта.

Причиной неожиданного нуля было слишком узкое окно свежести: позиции старше 300 секунд
отбрасывались, хотя OpenSky, очередь и streaming job могут давать большую задержку.
Кроме того, часовой интервал aggregation давал слишком редкие моментальные снимки.

Исправлено:

- `build_totals()` считает `active_flights` и `airborne` по одному набору свежих строк
  `positions_current` с `on_ground = false`, поэтому эти поля согласованы;
- `dashboard_trend.active_aircraft` формируется из `totals.active_flights`;
- `flights_open` не читается aggregation job;
- окно свежести по умолчанию увеличено с 5 до 15 минут;
- scheduler aggregation по умолчанию запускается каждые 5 минут вместо одного часа;
- исторические показатели аэропортов, маршрутов и производителей при каждом запуске
  всё так же рассчитываются за последние 24 часа;
- параметры вынесены в `POSITION_FRESHNESS_SECONDS=900` и
  `AGGREGATE_INTERVAL_SECONDS=300`;
- тест aggregation проверяет расчёт snapshot по свежим позициям и нули для пустого
  набора;
- описание показателей обновлено в `docs/database.md` и `spyt/README.md`.

## Результаты retention-теста сегментации — 19 августа 2026

Часовой интеграционный прогон дал 369 закрытых сегментов: 125 `landing` и 244
`timeout`; базовые инварианты не нарушены. Разбор истории показал два систематических
эффекта.

Первый — короткие сегменты `landing` с одинаковыми аэропортами создавались
последовательностью `ground -> airborne -> ground`. Одиночный ложный
`on_ground=false` немедленно открывал рейс, а последующие ground-точки закрывали его.
Теперь `job_segment` не записывает `landing` и airport events, если известные
аэропорты вылета и прилёта совпадают, а длительность сегмента не превышает
`GROUND_GLITCH_MAX_SECONDS`. Более длинные возвраты в тот же аэропорт сохраняются.
Правило применяется при всех вариантах подтверждения посадки, включая закрытие
зависшего состояния.

Второй — история борта могла содержать продолжение воздушной траектории, хотя
сегмент уже был закрыт как короткий `timeout`. Причина: watermark продвигался по
настенному времени, а выборка использовала `time_position`; строки, записанные
streaming job позже продвижения watermark, пропускались навсегда. Теперь
`watermark_ts` является курсором по `enriched_at`: отбор новых и предыдущих строк
делается по времени появления обогащённой записи, а обработка и границы рейса
по-прежнему упорядочены по `time_position`. Это не требует изменения схемы
`pipeline_job_state`, но меняет семантику сохранённого поля.

При выкладке на уже существующий префикс старый event-time watermark нельзя
продолжать как enrichment-time cursor: строку `job_segment` в `pipeline_job_state`
нужно инициализировать заново либо использовать новый тестовый префикс. Таблицы
рейсов и checkpoint streaming job удалять без отдельного решения не следует.

Добавлены регрессионные тесты: короткий same-airport переход отбрасывается, а
same-airport сегмент длиннее glitch-окна сохраняется.

Проверены `python3 -m py_compile` для `job_aggregate.py` и `run_aggregate.py`, а также
`git diff --check`. Pytest в текущем окружении не запущен: команда `pytest`
отсутствует (`command not found`). После развёртывания запускать `run_aggregate.py`
без `--skip-upload`, чтобы новая версия job попала в Cypress.

Основной диагноз — гонка между фиксированным `computed_at` aggregate job и
обновлением dynamic table `positions_current`. Таблица хранит только последнюю
версию строки каждого `icao24`. Spark DataFrame вычисляется лениво: после фиксации
`computed_at`, но до фактического чтения, streaming job может заменить строки
позициями с `time_position > computed_at`. Aggregate исключает такие «будущие»
строки, однако предыдущих версий борта в `positions_current` уже нет. Поэтому борт
исчезает из snapshot целиком. При неудачном взаимном тайминге обновления всего
мирового snapshot это даёт ровно ноль. Та же гонка объясняет, почему обычные
ненулевые trend-точки были на 5–13% ниже реконструкции из истории.

Увеличение freshness-окна не исправит дефект: проблема находится на верхней границе
`time_position <= computed_at`. Корректный эталонный расчёт должен выбирать из
`positions_history` последнюю позицию каждого борта в интервале
`[computed_at - freshness, computed_at]`. Более дешёвое исправление требует сначала
зафиксировать и материализовать единый snapshot `positions_current`, а затем выбрать
согласованный `computed_at`; также нужен небольшой допуск на рассинхронизацию часов.
Все dashboard-выходы должны вычисляться из одного зафиксированного поколения данных.

## Фильтрация типов OpenSky в ingest — 21 августа 2026

Чтобы уменьшить объём `positions_raw`, `positions_history` и нагрузку последующих
Spark jobs без изменения набора таблиц, фильтр типов добавлен непосредственно после
разбора ответа OpenSky и до записи raw. Endpoint по-прежнему вызывается с
`extended=1`, поэтому категория находится в `states[i][17]`.

Ingest сохраняет категории `null`, 0 и 1 с отсутствующей или неизвестной ADS-B
emitter category, а также самолётные категории 2–7: Light, Small, Large,
High Vortex Large, Heavy и High Performance. Production snapshot показал, что
`null`/0/1 составляют около 97,7% строк и включают множество обычных Airbus и Boeing,
поэтому отсутствие категории не может служить основанием для удаления. Явно
не-самолётные категории 8–20, включая Rotorcraft, Glider, UAV и surface vehicles,
исключаются. Неожиданные числовые значения вне известного диапазона сохраняются для
последующей классификации и отражаются в диагностическом логе. Значения несовместимого
с YTsaurus-схемой типа логируются и исключаются.

Фильтрация не уменьшает размер HTTP-ответа и расход OpenSky credits: весь ответ всё
равно скачивается и разбирается. Добавочная CPU-нагрузка ingest — одна проверка
категории на state vector; число записей в YTsaurus и нагрузка streaming/segment jobs
при этом уменьшаются. Лог ingest теперь показывает число записанных строк и исходное
число строк ответа, чтобы коэффициент фильтрации можно было измерить на production.
Проверены сохранение неизвестных и неожиданных категорий, исключение известных
не-самолётных категорий, state vector без extended category и прежняя валидация
координат/времени.

После обогащения streaming job применяет второй, консервативный уровень фильтрации.
Поле `icaoaircrafttype` загружается из OpenSky Aircraft Database в `ref_aircraft` и
переносится в `positions_history`/`positions_current`. Для входных категорий
`null`/0/1 префиксы `H`, `G` и `T` считаются подтверждёнными helicopter, gyrocopter
и tilt-wing/tiltrotor и исключаются из обеих таблиц. Префиксы `L`, `S`, `A` считаются
самолётами. Пустые, неожиданные типы и неожиданные категории сохраняются как
`unknown`. Явная OpenSky category имеет приоритет над справочником. Поле
`aircraft_class` сохраняется в history/current и имеет для записанных строк значения
`aircraft` или `unknown`; внутренний вердикт `non_aircraft` логируется, но такие
строки отбрасываются. Каждый microbatch логирует количества `aircraft`,
`non_aircraft` и `unknown`.

Это изменение расширяет схемы существующих таблиц. Одного перезапуска streaming job
недостаточно: перед выкладкой необходимо обновить схемы `ref_aircraft`,
`positions_history` и `positions_current`, а `ref_aircraft` перезагрузить из CSV.
`bootstrap_service --overwrite` пересоздаёт таблицы и удаляет их данные, поэтому его
нельзя применять к production history/current без отдельного плана миграции.

Robinson R44 и AW139. Следовательно:

- отсутствие ADS-B emitter category не означает неизвестный тип транспорта;
- строгий ingest-фильтр 2–7 давал около 97,7% false negative и удалён;
- `categoryDescription` слишком редко заполнено и не годится как основной источник;
- unknown нужно сохранять, а подтверждённые rotorcraft отделять после enrichment;
- `icaoaircrafttype` выбран как структурированный второй источник классификации.

### Production-проверка двухуровневого фильтра после выкладки

В длительном запуске с новым фильтром логи streaming job для batch 4–13 дали
95 425 входных позиций. До удаления второго уровня распределение было следующим:

| Вердикт | Позиций | Доля входа | Действие |
|---|---:|---:|---|
| `aircraft` | 67 267 | 70,49% | сохранить |
| `unknown` | 26 791 | 28,08% | сохранить консервативно |
| `non_aircraft` | 1 367 | 1,43% | удалить |

После удаления `non_aircraft` записано 94 058 позиций. В отдельном доступном срезе
`positions_history` находилось 23 582 строки: 16 902 `aircraft` (71,67%) и 6 680
`unknown` (28,33%). Распределение хорошо согласуется с логами микробатчей; точного
совпадения быть не должно из-за разных моментов выборки, TTL и замены одинаковых
ключей `(icao24, time_position)` в dynamic table. Доли по последовательным обычным
микробатчам также оставались стабильными. На первом уровне ingest явные категории
8–20 составляли примерно 0,21–0,26% ответа в показанных snapshot; отдельно от них
отбрасывались строки без валидной позиции.

Чтобы определить причину оставшихся `unknown`, их сгруппировали по
`icaoaircrafttype`. Среди 23 883 unknown-позиций, относящихся к 2 974 уникальным
`icao24`, результат был таким:

| `icaoaircrafttype` | Позиций | Уникальных объектов | Доля объектов |
|---|---:|---:|---:|
| пустое значение | 23 872 | 2 973 | 99,97% |
| `C68A` | 11 | 1 | 0,03% |

`C68A` похож на ICAO type designator Cessna 680A, то есть на значение поля
`typecode`, ошибочно или нестандартно попавшее в `icaoaircrafttype`. Расширять
классификацию на весь префикс `C` по одной такой строке небезопасно.

Для 2 973 объектов с пустым `icaoaircrafttype` покрытие другими полями справочника:

| Поле | Объектов с непустым значением | Доля unknown-объектов |
|---|---:|---:|
| `registration` | 152 | 5,11% |
| `typecode` | 57 | 1,92% |
| `model` | 112 | 3,77% |

Эти множества могут пересекаться, поэтому проценты нельзя складывать. Даже
`registration`, самое заполненное из проверенных полей, отсутствует у 94,89%
unknown-объектов. Значит, основной предел классификации задаёт не правило префиксов,
а отсутствие справочных данных для наблюдаемых `icao24`.

Production-вердикт: двухуровневый фильтр выполняет поставленную консервативную
задачу. Он уверенно классифицирует около 70–72% входа как самолёты, удаляет явно
не-самолётные объекты и не теряет почти треть потока, для которой доказательств
недостаточно. Практически все оставшиеся `unknown` не имеют `icaoaircrafttype`,
поэтому добавление новых префиксов к текущему правилу заметного эффекта не даст.
Небольшой дополнительный охват возможен эвристиками по `typecode`/`model`, но он
ограничен несколькими процентами unknown-объектов, потребует отдельного справочника
типов и повысит риск ложной классификации. Существенно уменьшить `unknown` можно
только обновлением или дополнением `ref_aircraft` из более полного источника по
`icao24`. Для текущего источника и поля `icaoaircrafttype` фильтр находится близко
к практическому потолку; агрессивно отбрасывать `unknown` нельзя.

Количество строк с конкретным `snapshot_time` в dynamic `positions_history` может
уменьшаться во время работы ingest. Ключ таблицы — `(icao24, time_position)`; если
следующий snapshot приносит тот же ключ, строка заменяется и получает новый
`snapshot_time`. Это не само по себе потеря streaming job. Для стабильного анализа
одного snapshot ingest нужно остановить либо учитывать эту семантику замены.

`aircraft_class` пока намеренно не протянут в `flights_open` и `flights_segments`.
Segment job сохраняет состояние рейса между batch-запусками, а вердикт справочника
может измениться после его обновления; нужно отдельно определить правило агрегации
класса на весь рейс и мигрировать обе flight-таблицы. Для карты и диагностики
history/current уже содержат необходимый вердикт.

Текущая работа ограничена каталогом `pipeline`: backend и frontend не изменялись.
Проброс `aircraft_class` через API и выбор иконок остаются отдельной задачей других
компонентов после стабилизации pipeline-схемы.

## Раздельные TTL таблиц — 21 августа 2026

Единый `DATA_RETENTION_SECONDS` удалён: он не позволял сократить объём
`positions_history`, не обрезав одновременно данные суточных dashboard-витрин.
Вместо него используются четыре независимые переменные:

```text
POSITIONS_HISTORY_RETENTION_SECONDS=36000
FLIGHTS_SEGMENTS_RETENTION_SECONDS=172800
AIRPORT_EVENTS_RETENTION_SECONDS=172800
DASHBOARD_TREND_RETENTION_SECONDS=172800
```

History по умолчанию хранится 10 часов. Это соответствует режиму, в котором OpenSky
credits хватает примерно на одну пятичасовую сессию, но означает явное продуктовое
ограничение: backend не сможет вернуть часть трека старше 10 часов. TTL history обязан
быть только положительным и не связан с dashboard window.

Сегменты, airport events и trend по умолчанию хранятся двое суток. Каждый из этих
TTL валидируется как строго больший `DASHBOARD_WINDOW_SECONDS`, чтобы суточные
агрегации не теряли исходные данные. Bootstrap новых таблиц и
`bootstrap_service.apply_retention` для существующих таблиц применяют соответствующий
TTL отдельно. Физическое освобождение места после уменьшения TTL остаётся
асинхронным и зависит от compaction YTsaurus. Добавлены тесты независимых значений,
дефолтов и ограничений относительно dashboard window. Полный локальный прогон после
изменения: 104 passed, одно известное предупреждение PySpark о pandas 3.x.
