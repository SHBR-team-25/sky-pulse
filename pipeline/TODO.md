# TODO: retention и актуальность таблиц позиций

## Общее решение по retention

Для pet-проекта не строить отдельный архивный контур и не заводить собственную
cleanup-job без необходимости. Ввести одну переменную окружения
`DATA_RETENTION_SECONDS`, определяющую срок хранения производных исторических данных.
Применять её к:

- `positions_history`;
- `flights_segments`;
- `airport_events`;
- `dashboard_trend`.

Предпочтительный механизм — встроенный TTL sorted dynamic tables YTsaurus. При
создании этих таблиц нужно задавать TTL и `min_data_versions=0`: со стандартным
`min_data_versions=1` последняя версия каждого уникального ключа останется навсегда.
Значение из env задаётся в секундах, а в атрибуты YTsaurus переводится в миллисекунды.

TTL YTsaurus считается по commit/write time, а не по бизнес-колонкам
`time_position`, `end_ts`, `event_ts` или `computed_at`, и удаление происходит
асинхронно во время compaction. Для этого проекта такое приближение приемлемо:

- позиции обычно записываются вскоре после наблюдения;
- сегмент и события записываются при закрытии рейса;
- точка trend записывается в момент расчёта.

При разборе старого backlog данные могут прожить дольше заданного event-time окна,
но не будут удалены преждевременно. Это безопаснее и проще отдельной cleanup-job.

Retention должен быть строго больше `DASHBOARD_WINDOW_SECONDS` с запасом на задержки
и пропущенные запуски. Разумное начальное значение для MVP — 7 дней при текущем
dashboard window в 1 день. Это одновременно определяет максимальный горизонт
восстановления: если `job_segment` не работает дольше retention, часть уже записанной
истории может исчезнуть до обработки. Ограничение следует явно документировать и
контролировать мониторингом watermark/lag.

Настройка bootstrap влияет только на вновь создаваемые таблицы. Для существующих
таблиц потребуется отдельное однократное изменение атрибутов и remount; нельзя считать,
что добавление env автоматически поменяет уже созданные объекты YTsaurus.

`positions_current` в общую TTL-политику не включать: её актуальность определяется
backend-фильтром, описанным ниже. `flights_open`, справочники, job state и snapshot-
витрины также не включать. Dashboard-витрины totals/top/routes/manufacturers
перезаписываются, поэтому бесконечного роста актуальных строк у них быть не должно.

## `positions_current`: устаревшие позиции

### Проблема

`positions_current` — сортированная dynamic table с единственным ключом `icao24`.
Streaming job выбирает самую новую позицию борта только внутри очередного микробатча
и записывает её по этому ключу. Если борт больше не появляется во входном потоке, его
последняя строка не удаляется и остаётся в таблице бессрочно.

Это допустимо, если понимать таблицу как «последняя известная позиция», но backend
сейчас читает её как список текущих позиций. В результате API может возвращать давно
исчезнувшие борта, а карта — показывать самолёты-призраки. То же относится к запросу
последней позиции конкретного `icao24`.

Есть связанный риск: streaming job сравнивает позиции только внутри микробатча, но не
с уже записанной строкой. Запоздавший микробатч теоретически может заменить более
новую позицию более старой.

### Предпочтительное решение

Оставить `positions_current` хранилищем последней известной позиции и в backend
ввести конфигурируемое понятие свежести позиции.

Backend должен добавлять временной диапазон непосредственно в запрос к YTsaurus,
совмещая его с bounding box:

- не возвращать позиции старше выбранного порога;
- не возвращать позиции из будущего;
- применять то же правило к списку позиций и к запросу одного борта;
- при запросе устаревшего борта определить явную семантику: например, отвечать как
  для отсутствующего борта либо отдельно обозначать stale-состояние;
- не загружать всю таблицу в Java для последующей фильтрации.

Начальное значение можно согласовать с dashboard:
`POSITION_FRESHNESS_SECONDS=900`. Для более живой карты после замера реальной частоты
OpenSky можно выбрать меньший порог, например 2–5 минут.

Это основной вариант: он отделяет «последнюю известную позицию» от «позиции, которую
ещё можно считать текущей» и не требует удалять полезное последнее состояние.

### Другие варианты

1. Периодически удалять устаревшие ключи из `positions_current`. Это ограничивает
   физический размер таблицы, но смешивает API-семантику свежести с политикой хранения.
   Удаление в dynamic table освобождает место не сразу, а после compaction.
2. Настроить TTL или удаление по watermark в YTsaurus. Обычный table TTL основан на
   времени записи версии, а не на `time_position`; watermark может работать по
   пользовательской timestamp-колонке, но сложнее в эксплуатации.
3. Перестраивать snapshot поколениями во временную таблицу и атомарно переключать
   активное поколение. Это даёт строгий snapshot, но заметно усложняет pipeline.

Отдельно нужно обеспечить монотонность `time_position` между микробатчами, чтобы
запоздавшее событие не затирало более новую последнюю позицию.

## `positions_raw`: автоматическая очистка queue

### Что поддерживает YTsaurus

Queue Agent умеет автоматически делать trim очереди через атрибут
`@auto_trim_config`:

- `enable=true` разрешает trim до минимального offset среди всех vital consumers;
- если vital consumers нет, такой trim не выполняется;
- `retained_rows` позволяет гарантированно оставить некоторое число строк в каждой
  partition;
- `retained_lifetime_duration` задаёт временное окно удержания строк;
- trimming логически удаляет начальный префикс каждой partition; физическое место
  освобождается, когда целые начальные chunks могут быть удалены.

Vital consumer защищает непрочитанные им данные только при включённой политике
автоматического trimming. Одна лишь регистрация consumer как vital не включает
очистку очереди.

### Текущее состояние проекта

Consumer регистрируется с `vital=true`, но при создании `positions_raw` проект не
задаёт `@auto_trim_config` и не задаёт TTL/mount-настройки очистки. Следовательно,
из репозитория нельзя заключить, что очередь автоматически очищается; наоборот,
bootstrap её не настраивает. Фактические атрибуты уже созданной таблицы нужно отдельно
проверить в кластере, потому что их могли установить вручную.

Кроме того, bootstrap создаёт consumer по пути
`positions_raw_consumer_second_job`, тогда как streaming launcher по умолчанию
использует `positions_raw_consumer`. Нужно проверить регистрации и фактический путь
запущенной streaming operation: ошибочный или забытый vital consumer может навсегда
удерживать trimming на старом offset.

### Предложение

Для `positions_raw` включить Queue Agent auto-trim по vital consumers и оставить
небольшой запас через retained rows или retained lifetime. Единственный рабочий
streaming consumer должен быть vital; диагностические и временные consumers —
non-vital. Неиспользуемые vital-регистрации следует удалять осознанно после проверки,
что они больше не нужны.

Очередь не следует включать в общую `DATA_RETENTION_SECONDS`: у неё другая семантика.
Основная граница удаления — подтверждённый offset vital consumer, тогда как retention
производных таблиц является обычным сроком хранения уже обработанных данных.

Дополнительно можно задать аварийный верхний предел хранения через TTL ordered
dynamic table. Это защищает кластер от бесконечного роста при consumer, который
навсегда остановился, но ослабляет гарантию «не терять непрочитанное»: после жёсткого
срока данные будут потеряны. Для выполнения NFR3 основной политикой должен оставаться
trim по offset vital consumer, а аварийный TTL следует выбирать существенно больше
максимально допустимого времени восстановления pipeline.

Перед включением проверить наличие Queue Agent и текущие `@queue_status`,
`@queue_partitions`, registrations, consumer offsets и lag на целевом кластере.

## `positions_history`: неограниченное накопление

### Проблема

Каждая позиция записывается в `positions_history` с уникальным ключом
`(icao24, time_position)`. Повтор того же ключа обновит строку, но новые timestamps
создают новые ключи, поэтому таблица растёт вместе со всем потоком.

Проект не задаёт для неё retention, TTL, row-level TTL, watermark-очистку или
периодическую задачу удаления. Стандартные настройки версий dynamic table не решают
эту задачу: при `min_data_versions=1` последняя версия каждого уникального ключа
сохраняется, а каждый ключ истории обычно имеет только одну версию.

Историю сейчас используют:

- `job_segment`, который читает новые строки после своего event-time watermark и
  небольшой диапазон перед watermark для восстановления перехода;
- backend треков, который читает позиции новее `now - sinceSeconds`.

После успешного продвижения watermark сегментации очень старая история pipeline уже
не нужна, однако пользовательский endpoint трека требует заранее определённой глубины
хранения. Сейчас `sinceSeconds` фактически не ограничивает запрашиваемый период сверху,
поэтому контракт retention не определён.

### Предпочтительное решение

Применить общую `DATA_RETENTION_SECONDS` через table TTL с
`min_data_versions=0`. Максимальный `sinceSeconds` backend ограничить тем же сроком,
чтобы API не обещал историю, которая уже могла быть удалена.

Watermark `job_segment` и её отставание нужно мониторить. Retention задаёт конечный
срок восстановления, поэтому его значение должно с запасом покрывать ожидаемые
простои segment job. Для MVP предлагается 7 дней.

### Другие варианты

1. Отдельная cleanup-job по `time_position` и watermark сегментации. Она даст точный
   event-time retention, но добавит ещё одну джобу, расписание, обработку ошибок и
   tombstones; для текущего масштаба это неоправданно.
2. Row-level TTL через системную колонку `$ttl`. Требует изменения схемы и записи TTL
   для каждой строки; для единого срока хранения преимуществ перед table TTL мало.
3. YTsaurus watermark row merger по `time_position`. Он ближе всего к event-time
   retention и удаляет строки во время compaction, но требует аккуратной mount/runtime
   конфигурации и отдельного процесса, который безопасно двигает watermark.
4. Архивировать старые диапазоны в статические партиционированные таблицы, а в
   dynamic history держать только горячее окно. Это лучший долгосрочный вариант, если
   полная история нужна для аналитики, но для текущего MVP сложнее необходимого.

Для текущего проекта разумный порядок: включить общий table TTL, ограничить глубину
треков тем же контрактом и добавлять архивирование только при появлении требования
хранить полную историю.

## `flights_segments` и `airport_events`

Обе таблицы сейчас растут по мере закрытия рейсов. Dashboard читает из них только
фиксированное окно `DASHBOARD_WINDOW_SECONDS`: события фильтруются по `event_ts`, а
сегменты — по `end_ts`. Поэтому хранить их бесконечно для текущей функциональности
не нужно.

Применить к обеим таблицам общую `DATA_RETENTION_SECONDS` через table TTL и
`min_data_versions=0`. Retention обязан быть больше dashboard window с запасом.
Отдельная очистка по `event_ts`/`end_ts` для MVP не нужна: время записи закрытого
рейса достаточно близко к времени события, а поздно обработанный backlog просто
сохранится немного дольше.

Если в будущем появятся отчёты за месяцы или обучение на полной истории, старые
сегменты и события нужно будет экспортировать в статические партиционированные
таблицы до истечения TTL. Это не входит в текущий MVP.

## `dashboard_trend`

`dashboard_trend` добавляет новую строку с ключом `computed_at` при каждом запуске
aggregate job и поэтому тоже растёт бесконечно. Применить к ней ту же
`DATA_RETENTION_SECONDS` через table TTL и `min_data_versions=0`.

Здесь table TTL особенно естественен: `computed_at` практически совпадает со временем
записи. Отдельная cleanup-job не нужна. Backend/будущий analytics API не должен
запрашивать trend глубже общего retention.
